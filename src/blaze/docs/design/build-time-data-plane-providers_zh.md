# 构建时数据面提供者

[English](build-time-data-plane-providers.md)

## 目的

Blaze 提供源码级数据面合同，使下游开发者可以在不修改 Blaze 源码树的情况下，把自定义
资源实现与守护进程组合成一个二进制文件。最终实现由构建过程确定，不从插件目录发现，
不由租户请求选择，也不能通过标准守护进程配置切换。

标准 `blazed` 二进制始终使用现有文件实现。下游开发者可以在扩展软件包中实现
`DataPlaneProvider`，把 `blazed` 作为库依赖，再将实现交给
`BlazeDaemonBuilder`。

## 兼容边界

该合同是 Rust 源码接口，不是稳定的动态库二进制接口。提供者二进制必须固定彼此兼容
的以下内容：

- `blaze-provider-api`；
- `blaze-provider-conformance`；
- `blazed` 与 `blaze-core`；
- Rust 工具链；
- 最终构建使用的依赖锁文件。

`ProviderDescriptor.contract_version` 可以在运行时拒绝明显不匹配的合同版本，但不能
替代源码版本和依赖版本固定。

## 可复现且保护隐私的构建

Rust 工具链可能在诊断信息和元数据中保留绝对源码路径。为了得到可复现的分发制品，
应使用稳定的源码根目录，或通过 `rustc` 的 `--remap-path-prefix` 重映射构建路径；
Cargo 依赖路径也应采用同一规则。分发包只包含 Git 跟踪的源码和明确声明的发布制品，
不得复制 `.git`、`target`、本地配置或测试生成文件。

这些检查用于保证可复现性、开发者隐私和部署凭据安全，不能代替对已交付行为的说明。
发布前，应把归档文件清单与声明的发布输入逐项比较，并检查二进制中的可打印字符串，
确认没有意外包含本机路径、主机标识、凭据或未声明的配置。扩展有意发布的产品标识和
设置应在该扩展的发布说明中明确记录。

## 生命周期合同

基础合同只覆盖沙箱创建和删除。每次修改都绑定预先选定的沙箱标识、请求标识、操作
标识、租约标识和代次。成功流程如下：

| 操作 | 必须满足的语义 |
|---|---|
| `probe` | 在不分配沙箱资源的前提下检查依赖和权限。 |
| `prepare` | 创建一个由提供者持有的租约，并返回路径资源或已打开恢复资源。 |
| `inspect` | 在不修改资源的前提下观察已知租约的准确状态。 |
| `commit` | 在发布公开状态前，确认后端已经就绪。 |
| `finalize` | 在匹配的公开状态持久化后完成所有权交接。 |
| `stop` | 记录后端已经停止使用资源，同时保留清理所有权。 |
| `release` | 证明已停止租约持有的全部资源都已删除。 |
| `abort` | 撤销尚无持久公开所有者的准备中或已提交租约。 |

每次成功转换必须保留相同的提供者、请求、操作和租约标识，并且只把代次增加一次。如果
调用可能已经产生副作用却无法确认结果，提供者返回 `OutcomeUnknown`；Blaze 会先调用
`inspect`，再判断能否安全补偿。

`prepare` 可以返回两类资源：

- `PreparedResources::PathBacked`：保留现有文件存储布局；
- `PreparedResources::OpenedRestore`：为经过校验的模板恢复转交带类型的根盘和客户机
  内存描述符。

只有提供者声明对应能力时，Blaze 才接受已打开资源。Blaze 会在启动后端前核验租约和
资源形状。如果资源形状无效，但返回的租约绑定仍能安全识别，Blaze 会调用 `abort`；
Blaze 不会使用不可信绑定执行补偿。

## 组合方式

扩展软件包实现 `DataPlaneProvider`，定义所需的资源配置和持久状态，并把实现错误映射为
与提供者无关的 `ProviderError` 类别。面向具体用途的命令程序作为组合入口。仓库内提供
两个可以执行的示例：

- [`minimal_provider.rs`](../../crates/blaze-provider-conformance/examples/minimal_provider.rs)
  使用完整的基础接口实现运行可复用的创建和删除检查；
- [`custom_provider_daemon.rs`](../../crates/blazed/examples/custom_provider_daemon.rs)
  将同一个提供者交给 `BlazeDaemonBuilder` 并启动守护进程。

在 `src/blaze` 目录中构建并检查这两个入口：

```bash
cargo run -p blaze-provider-conformance --example minimal_provider --locked
cargo run -p blazed --example custom_provider_daemon --locked -- --help
```

守护进程示例直接接收 `--daemon-config <路径>` 和
`--resource-root <绝对目录>`，不使用标准二进制的 `daemon start` 子命令。共享的
`ExampleFileProvider` 会创建真实稀疏文件，但有意不实现持久化和任何可选扩展。生产
提供者还必须验证真实后端、失败补偿、并发和故障恢复。

构建器会在 Blaze 创建守护进程目录前核验提供者描述并执行 `probe`。探测失败会直接
终止启动，不会构造标准文件提供者来替换失败的构建时提供者。

## 扩展配置

`DaemonConfig` 与具体提供者无关，也不能在运行时选择构建时扩展。每个扩展在自己的
软件包和组合二进制中定义所需配置和资源映射。扩展返回 Blaze 的值仅限公开、与具体
实现无关的类型和稳定的 `ProviderError` 类别；Blaze 不接收提供者生成的任意错误文本。
扩展代码如需输出额外诊断，应由开发者按照部署环境的日志策略自行实现。

通过管理接口返回的名称属于扩展的版本化产品合同，应由扩展维护者明确说明。传输端点、
资源映射和提供者专用设置留在提供者软件包及其运维文档中，使 Blaze 配置可以被彼此
独立的实现复用。

Blaze 使用明确的沙箱管理响应结构。该结构包含已经说明的生命周期、策略和运行后端
字段，但不包含数据面租约或恢复记录。因此，在构建时选择提供者不会暗中扩展 HTTP
响应结构。

Blaze 自身的贡献也遵循可复用合同原则。公开类型、注释、示例、测试材料和诊断信息只
描述可观察的资源角色、能力、生命周期结果和稳定错误类别。示例必须仅依靠 Blaze
仓库跟踪的源码即可理解和运行。提供者专用资源拓扑和配置由相应提供者自行定义和说明。

第一版仍要求配置现有 `[storage]` 文件目录。Blaze 的旧检查点、休眠和周期同步流程仍
使用文件 `StorageProvider`。注入主要数据面提供者只改变创建和删除，不会把这些旧流程
自动扩展到提供者持有的沙箱。

## 已支持和暂缓的行为

| 场景 | 当前状态和前置条件 |
|---|---|
| 使用路径资源从普通镜像创建 | 支持 |
| 使用路径资源从模板创建 | 支持 |
| 使用已打开根盘和客户机内存资源从模板创建 | 提供者声明能力后支持 |
| 使用已打开恢复资源从普通镜像创建 | 在启动后端前拒绝 |
| 构建时提供者探测失败 | 启动失败，不回退文件实现 |
| 守护进程重启后接管提供者租约 | 要求实现可选资源清单合同，且后端支持按身份接管 |
| 提供者持有的检查点和回退 | 不支持 |
| 提供者持有的休眠和恢复 | 不支持 |
| 提供者容量和可复用资源池 | 不支持 |
| 运行时发现动态库或进程插件 | 不支持 |

不支持重启接管的提供者不能被描述为适合持久工作负载的生产实现。资源清单合同及其
故障关闭规则见[提供者重启核对](provider-reconciliation_zh.md)。检查点、休眠和容量仍应
分别增加可选合同，不能在基础接口中提前放入没有使用者的方法。

## 验证要求

扩展实现至少应完成：

1. 使用隔离资源运行 `blaze-provider-conformance::exercise_create_delete`；
2. 覆盖全部结果不明和失败补偿分支；
3. 证明不支持的来源会在产生副作用前失败，并且不会选择另一个提供者；
4. 证明真实后端使用的正是租约返回的资源；
5. 删除后确认不存在活动后端、附件、提供者资源或仍可领取的租约；只有不再持有资源的
   幂等记录或清理标记可以保留；
6. 确认面向 Blaze 的接口、日志、指标和一致性证据遵守公开合同，并在扩展自身的开发者
   文档和运维文档中完整说明其资源模型。

一致性软件包只核验与提供者无关的状态和资源形状；具体扩展仍需自行证明正确性和生产
就绪程度。
